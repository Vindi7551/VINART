# 设计草图阶段 —— `design-sketch`

这一阶段把一份「创意方案」变成**可渲染的版式规格**（`design-sketch.json`），
再把它画成**草图**——一份给人审、也给生图模型当构图控制的蓝图。

**它自包含**：契约、校验、渲染、编译器都住在这个目录里。
**改这个阶段的任何东西之前，先读这份文档。**

---

## 一、这个目录里有什么

| 文件 | 是什么 |
|---|---|
| `design-sketch.ts` | **契约（版式）**：类型定义，`tsc` 会盯着 |
| `design-sketch.md` | **给模型读的契约**：产 spec 时的唯一依据 |
| `design-appearance.ts` | **契约（外观）**：颜色 / 描边 |
| `render-style.ts` | **渲染参数**：配色与字体的**具体值**（可换的皮）|
| `validate.ts` | **校验**：`checkSketch` / `checkAppearance` |
| `render.ts` | **成品渲染**：DesignSketch → HTML（图用 `{{占位符}}` 待替换）|
| `sketch.ts` | **草图渲染**：DesignSketch → 草图 HTML（区域框 + 灰条 + 网格）|
| `shared.ts` | **共享几何**：`layerBox` / `wrap` / 修饰器 —— 两套渲染都用 |
| `runtime.ts` | **运行时**：读资产（配色 / 字体 / 图标）→ 渲出草图 PNG |
| `compile.ts` | **编译器**：创意方案 → spec → 校验 → 渲草图 → VLM 验收（多轮循环）|
| `README.md` | 本文件 |

**入口在 `scripts/`**（不属于本阶段，只是调用它的壳）：

```bash
npm run step src/workflow/design-sketch/compile.ts -- <方案.md>   # 编译器
npm run step scripts/render-sketch.ts -- <spec.json>              # 只渲草图
npm run step scripts/check-sketch.ts -- <spec.json>               # 只校验
```

### 这个阶段在整条链上的位置

```
创意方案（散文 / Markdown / JSON，格式不限）
      │
      ▼  compile.ts（多轮：产 spec → 静态校验 → 渲草图 → VLM 验收）
design-sketch.json · design-appearance.json · sketch.png
      │
      ▼  交给出图阶段（素材订单 → 生图 → final 组装）
```

**契约与消费者是单向依赖**：实现 `import type` 契约，契约不知道实现存在。
所以换渲染器、加新消费者（如「DOM → 分层 canvas」导出器）都不用动契约。

## 二、契约

| 文件 | 职责 | 生命周期 | 谁写它 |
|---|---|---|---|
| `design-sketch.ts` | **版式**：什么在哪、多大、字号、什么形状 | 永久（设计本身就是它）| LLM 产出 `design-sketch.json`，或人手写 |
| `design-appearance.ts` | **外观**：颜色、描边、用哪套皮 | 跟版式走，但**经常单独改**（换配色）| 人手写或另一步产出 |
| `render-style.ts` | **渲染参数**：配色与字体的**具体值** | 可换的皮 | 一般不动，引用资产库里的命名方案 |
| （`asset-order.ts`）| **素材订单**：这些图怎么生成 | 一次性——素材落盘即作废 | **不属于本阶段**，在 `src/schema/` |

> `asset-order` 服务的是**出图阶段**（谁生产图、用什么提示词、传哪几张参考图）。
> 它不在这个目录里，是因为**它不是设计草图的事**——版式只管引用文件名。

### 版式 vs 外观 — 判据只有一条

> **改它会不会让别的东西挪位置？** 会 → **版式**；不会 → **外观**。

所以 `fontScale`（字号）、`weight`（字重）属于**版式**——它们决定文字块占多大、
层级怎么拉开；而 `fill` / `color` / `stroke` 属于**外观**。

> 字重为什么在版式这一侧：**同一字号、不同字重，文字的宽度和视觉分量都不同**
> （在 `nowrap` + 自动缩字号的规则下，字重会直接改变文字块的实际宽度）。

**实测教训**：题目里让模型产「版式」，它却被问到配色——于是编出 `cold-dusk`、
`noir-amber` 这些不存在的方案名。**它本来就不该在这一步被问。**

### 两个文件怎么对齐

外观**按节点 id 索引**，不重复几何：

```jsonc
// design-sketch.json —— 只有版式
{ "layers": [ { "id": "card", "type": "shape", "shape": "rect",
                "rect": { "x": 0.06, "y": 0.06, "w": 0.4, "h": 0.2 } } ] }

// design-appearance.json —— 只有颜色
{ "palette": "warm-copper", "fontScheme": "slab-rokkitt",
  "layers": { "card": { "fill": "#F5F1EA" } } }
```

## 三、`design-sketch` 完整规范

### 3.1 ★ 三类节点

```
   图  ·  文字  ·  形状
```

任何平面设计 = **内容 × 排布**。内容只有两类（图 / 文字）；
排布靠**位置与尺寸**；而画面里那些"块"——框、底板、分区——是第三类。

| type | 是什么 | 独有必填 |
|---|---|---|
| `image` | 照片 / 场景 / 商品图 | `asset` |
| `text` | 要出现在画面上的文字 | `text` |
| `shape` | **一个形状块**：当框、当底板、当分区 | `shape` |

三类**都必须有** `id` 和 `rect`。

#### ★ 「框」是什么——最容易误解的一点

**「框住一张图」不是数据上的从属关系，而是两个独立节点位置重叠。**

```
image 节点（内容）  +  shape 节点（框）  两者位置重合 = 看起来"框住了"
```

所以**形状自己给自己尺寸**，不依赖任何内容。它可以是"比文字大得多的大圆"，
也可以和内容严丝合缝。

**谁在谁上面，由 `layers` 数组顺序决定**（先写的在下面）：

| 想要的效果 | 形状写在图的… |
|---|---|
| **底板**（垫在内容下面） | **前面** |
| **相框**（压在内容上面） | **后面** |

描边不填充 = 看起来是「框」；填充不描边 = 看起来是「底板」——
*颜色与线宽属外观，写 `design-appearance.json`。*

#### 四种形状

| `shape` | 是什么 | 典型用途 |
|---|---|---|
| `rect` | 矩形（可带圆角 `radius`）| 卡片底、底板、分区、斜切图块 |
| `ellipse` | 椭圆 / 圆 | 圆形徽章、大圆、头像位 |
| `arch` | 拱门（上圆下方）| 拱形图窗 |
| `triangle` | 三角形 | 装饰 |

**为什么是「枚举」而不是「任意顶点」**：
**模型选一个名字，远比算一串顶点坐标稳**——这正是项目已验证的那条原则：
**把「给数值」变成「选位置」**。而且任意顶点会让对齐、网格、间距全部失效
（形状的包围盒不再有意义）。

- **朝向不设参数**，交给 `transform.rotate`（尖朝上的三角形转 180° 就是尖朝下）
- **斜切不设形状**，交给 `transform.skewX`（它是变换，会改变包围盒）
- **有机形状**（飘带、水花）**不做成形状**——它们归**素材图**

#### 主次：不写字段，靠尺寸自然表达

数据里**不写**"这是主图"。主图自然就大、就居中；次级图自然就小、就在边上。
文字同理——主要文字字号大、字重高。

### 3.2 它刻意不包含什么

| 不包含 | 去哪了 | 归谁管 |
|---|---|---|
| 颜色 / 描边 | `design-appearance.json` | 外观（可换的皮）|
| 生图提示词 / 参考图角色 / 尺寸 | `asset-order.ts`（出图阶段）| 素材订单 |
| 光影 / 材质 / 效果 | 生图提示词 | 生图阶段 |
| 最终成图怎么组装 | 待定 | final 组装（另一道工序）|

### 3.3 草图是什么、不是什么

> ⚠️ **草图不是最终成品的预览，是「版式蓝图」。**

它不含任何具体图片，只描述"哪里有一块什么"——所以它能在素材还没生成时先出图
（零成本、3 秒）。用途有两个：**给人审版式**，以及**喂给生图模型当构图控制**
（实测模型真的认，连"圆形细节区"这种几何语义都能传达）。

**主体由 `image` 节点的 `rect` 给它留位置**——`fit: contain` 表示"完整放进去、
不要裁到主体"（商品图用），`cover` 表示"铺满、超出裁掉"（场景照用）。

### 3.4 与素材的连接点：只有文件名

`image.asset` 写的是**文件名**（如 `scene.png`）。
谁生产这个文件、用什么提示词、传哪几张参考图——**版式契约一概不管**。
素材文件还没生成时，草图照样能出（草图不引用图片）。

### 3.5 三条贯穿全局的规则

**规则 1：`layers` 是有序数组，顺序即叠放顺序。**
不要靠 CSS 层叠上下文去猜谁在谁上面——顺序是数据，不是副作用。

**规则 2：每个节点在 HTML 里必须落成一个带 `data-layer` 的容器。**
容器内部结构自由。这是「DOM → 分层 canvas」的前提：拆层工具需要知道
"哪些是节点"，才能"隐藏其它、只留目标"。
*实测教训*：不做隔离直接截，`locator.screenshot()` 截到的是**那片画面**，
会把上下其它节点一起截进去。

**规则 3：节点不得依赖父容器来实现自身效果。**
不能让某个节点的外观靠父级的 `background` / `opacity` / `mix-blend-mode` / `filter`。
每个节点必须能被单独截出来而不变样。

> 这条也是「框是独立节点」而不是「内容的属性」的原因之一：
> **独立节点能被单独截出来，属性不能。**

### 3.6 坐标系

所有位置与尺寸一律用 **0–1 的画布比例**，与分辨率解耦。
同一份版式渲 2000×2000 与 970×300 都成立。

⚠️ **永远相对画布**，不相对任何别的节点——因为节点之间是**平级**的，没有嵌套。
"框住某个东西"靠**位置重叠**实现，不靠父子关系。

> 这个简化是"没有嵌套"换来的：旧契约里"顶层相对画布、组内相对组"，
> 同一个 `x:0.5` 在两层含义不同，是个持续的混乱来源。

### 3.7 变换：旋转与斜切

`transform` 是**可选的整块**，里面每个字段也都可省：

```jsonc
"transform": {
  "rotate": -8,                     // 度，顺时针为正。省略 = 不转
  "skewX": 0.15,                    // 顶边相对底边水平偏移的比例。省略 = 不斜切
  "origin": { "x": 0.5, "y": 1 }    // 支点，相对 rect 自身。省略 = 中心
}
```

**⚠️ 最重要的约定：变换不参与布局计算。**

| | 参与布局计算吗 |
|---|---|
| `rect` | **参与** —— 对齐、间距、网格、溢出检测全靠它 |
| `transform` | **不参与** —— 只改变画面，别的什么都不动 |

**所以它们是两个字段，不是合成一个。** 一个转过（或斜切过）的矩形
**没有「边」**、只剩角点，"左边缘对齐"这类说法本身就退化了。

**实现**：CSS 天然就是「先布局、后 `transform`」，零成本。
`origin` 等价于 `transform-origin`（百分比是**相对元素自身**，不是画布）。

**代价**：「数据上对齐」与「看起来对齐」会有偏差 → 靠**看图**发现（人审 / VLM）。
校验器会对"变换后溢出画布"给 warn，但**不会**检查"看起来有没有对齐"。

### 3.8 草图的视觉语言

草图是**给人审、给模型读**的蓝图，图形语言是规范过的，不要随意改：

| 元素 | 画法 | CSS |
|---|---|---|
| **文字** | 灰条（**高度 = 字号**，宽度 = 块宽）| `.sbar` |
| **图位** | **虚线框** | `.sbox` |
| **已定下来的面**（形状块）| **实心浅色块** | `.sfill` |
| **辅助网格** | **12 等分 + 中心十字**，画在最底层 | `.sgrid` / `.sgrid-axis` |

**三条容易搞错的**：

1. **虚线框是「图位」的专属标记** —— 形状块改用实心块。
   早先两者都画虚线框，读图时分不清"这里要放照片"还是"这里是个块"。
2. **灰条长度 ≠ 字号** —— 长度是**块宽**（版式给定的），**高度**才反映字号。
   VLM 验收时反复误读这一点，已在提示词里校准。
3. **辅助网格是参照，不是骨架** —— 12 × 12 是为了两件事：
   **读数方便**（整数百分比），以及**等分方便**（12 能被 2 / 3 / 4 / 6 整除）。
   元素可以贴着格线排，也可以**故意偏离**来制造张力——
   **校验器不会因为"没对齐网格"报任何错。**

> 网格**不进数据**：它只是画在草图上给人（和 VLM）读数的辅助线。

### 3.9 给模型的三条约定（正文在 `design-sketch.md`）

| 约定 | 为什么 |
|---|---|
| **不写颜色、不写光影** | 它们属于外观文件 / 生图提示词。实测：模型在产版式时被问配色，只会编造 `cold-dusk` 这类不存在的方案名 |
| **用「列网格」思考位置** | 最常见的错误是**近似对齐**（两个元素差 0.03，看起来就像没对齐）。边缘落在格线上，同类元素天然互相对齐 |
| **间距只用四档** | 垂直方向**没有标尺时，模型会来回震荡**：8 轮实测里它在「间距太平均」和「间距忽大忽小」两种相反的错误之间反复跳。四档：`tight 0.010` / `group 0.022` / `block 0.045` / `section 0.085`；同一层级必须同值、相邻层级差 2 倍以上 |

> **一条普适经验**：这两条约定的共同点是——**把「给数值」变成「选位置」**。
> 无限可能的坐标空间（随手给 0.37）模型掌握不好；
> 有限几档的选项（选第 3 列 / 选 group 档）它就稳得住。
> **形状也遵循同一条原则**（选一个名字，而不是算一串顶点）。

## 四、暂缓的能力

这些**设计过、验证过**，但当前契约里**刻意不含**——骨架先跑通，再逐个加回来。
留着这份记录，是为了加回来时**不重走弯路**。

### 4.1 分组 / 重复（原 `group` / `repeat`）

**要解决什么**：一张卡片由"底 + 图 + 文字"三个节点组成，三张卡就要写九遍坐标；
改一次卡片位置要改三处。

**当时的做法**：`group` 带 `children`，子层坐标**相对组盒子**（组 = 一个小画布）；
改组的 `x/y` 整体平移、改 `w/h` 整体缩放（连字号等比）。`repeat` 则是
"一次定义、N 份自动排"，`overrides[i]` 写各份的差异。

**当时的硬约束**：**组只能做几何变换，不得挂任何视觉属性**——否则组内节点
无法被单独截出来（违反规则 3）。需要组的底色时，在组内放一个铺满的形状节点。

**加回来时要想清楚的第一件事**：**嵌套会引入第二套坐标系**
（顶层相对画布、组内相对组），同一个 `x:0.5` 在两层含义不同。
当前契约"永远相对画布"的简洁，正是牺牲这个换来的。建议限制**最多两层**。

### 4.2 内联 SVG（原 `icon` / `badge`）

图标当时有两种给法：素材库按名取（`"icon": "ahorn"`）或直接内联源码（`"svg": "<svg…"`）。

**内联是「逃生舱」，不是主入口**——给一次性装饰用。三级阶梯：
**常用形状 → 用结构化字段**；**会重复用的装饰 → 进素材库**；
**一次性怪异装饰 → 才内联**。

**代价**：手写 SVG 路径容易出错；不可校验；不可复用。

**安全**：内联 SVG 能嵌 `<script>` 和事件属性，渲染时会在浏览器执行。
spec 虽在本地，却是 LLM 或人写的，不该默认信任——渲染器必须**拒绝**
含 `<script>` / `on*=` / `javascript:` 的 SVG，并报出节点 id。

### 4.3 声明式的对齐关系

现在全靠手算坐标。**这是"整齐"最薄弱的环节**——模型算不准，
而"近似对齐"恰恰是设计里最显眼的丑。

可能的形态：`align: { left: "@other-node" }` 这类**相对定位**，
或者 `distribute: "h-equal"` 这类**分布声明**。属"关系"维度，与"内容"正交。

## 五、一个实例长什么样

`design-sketch.json`：

```json
{
  "name": "DEMO",
  "title": "示例版式：左侧主图 + 右侧信息板",
  "canvas": { "width": 2000, "height": 2000 },
  "layers": [
    { "id": "panel", "name": "右侧信息板", "type": "shape",
      "shape": "rect", "radius": 0.25,
      "rect": { "x": 0.55, "y": 0.08, "w": 0.38, "h": 0.84 } },

    { "id": "hero", "name": "主图", "type": "image",
      "asset": "hero.png", "fit": "contain",
      "rect": { "x": 0.05, "y": 0.15, "w": 0.45, "h": 0.6 } },

    { "id": "title", "name": "主标题", "type": "text",
      "text": "Drei Dinge, die sofort auffallen",
      "rect": { "x": 0.6, "y": 0.15, "w": 0.28, "h": 0.07 },
      "fontScale": 0.045, "weight": 900 },

    { "id": "badge", "name": "圆形装饰", "type": "shape",
      "shape": "ellipse",
      "rect": { "x": 0.82, "y": 0.72, "w": 0.12, "h": 0.12 } }
  ]
}
```

**颜色不在这里**——写在同目录的 `design-appearance.json`：

```json
{
  "palette": "warm-copper",
  "fontScheme": "slab-rokkitt",
  "layers": {
    "panel": { "fill": "#F5F1EA" },
    "title": { "color": "#2B2118" },
    "badge": { "fill": "#B8722F" }
  }
}
```

**光影与材质也不在这里**——它们写在出图阶段的素材订单里：

```json
[
  {
    "file": "hero.png",
    "size": "2048x2048",
    "prompt": "Festlich gedeckte Geburtstagstafel in warmem Abendlicht, …",
    "references": [{ "ref": "@product", "role": "subject" }],
    "useSketchRef": true
  }
]
```

## 六、附：出图阶段的硬约束（实测）

> ⚠️ 这些**不属于设计草图阶段**（它们管的是生图），暂时记在这里，
> 等出图阶段建目录后移过去。写提示词或调用生图模型前请先对照：

| 约束 | 数值 / 规则 | 为什么 |
|---|---|---|
| 参考图数量 | **最多 2 张**同时传 | 超过就不可用（实测） |
| 输出尺寸 | **下限 3,686,400 像素**（约 1920²）| 低于此值被拒；竖构图用 `1440x2560`（正好卡下限，即 9:16） |
| 提示词禁词 | `Logos` / `Marken` / `Wasserzeichen` | 会触发 `InputTextSensitiveContentDetected`。**讽刺的是「不要出现品牌标识」这条指令本身就会触发**——要表达同样意思，改写成 `Ausser der Gravur enthält das Bild keine Schriftzeichen` |
| 内容审核 | **概率性**：同一份输入时过时不过 | 所以内核必须重试（实测：带 `size` 时成功、去掉 `size` 时被拦） |
| 参考图分辨率 | **不要压缩**（给足原尺寸） | 实测教训：曾把商品参考图压到 768px，雕刻小字读不清，生成时模型只能**编造**。改为原尺寸后逐字正确 |

> 最后一条尤其反直觉：**我们把证据弄糊了，再让它抄。**

# Photoshop 能力全景调查

> **调查日期**：2026-10-12
> **依据**：Adobe 官方 Photosop 桌面版用户指南目录（helpx.adobe.com）+ 桌面版发行说明（当前版本 **27.11 / 2026-09**）+ 官方《混合模式说明》。
> **目的**：为 Vinart 的「PS 化」路线提供**能力账本**——不是抄 PS，而是**逐条判断哪些能力可迁移、靠什么后端**。
> **用法**：先读 §0（导航），再按需查 §1（能力域），判断时用 §2（迁移性分级）与 §3（关键洞察）。

---

## §0 导航：本报告要回答三个问题

1. **PS 到底有哪些能力？**（§1，14 个能力域，逐域清单）
2. **哪些能落在 Vinart 现有的「HTML+CSS+SVG + Chromium」上？**（§2，迁移性分级表）
3. **哪些是真需要新后端（WASM / WebGPU / 外部模型）的？**（§2/§3）

> ⚠️ **前提**：Vinart **当前的渲染后端**是 **HTML+CSS(+SVG) + Chromium**——但这只是**当前实现，不是架构定义**。
> 文档模型须保持**后端无关**：未来可能是**混合渲染**（DOM 后端 + 光栅/GPU 后端），也可能是**多输出形态**（PNG / SVG / PDF / 分层）。
> 模型本身是**声明式 + 确定性**。所以"PS 化"= **在声明式模型里补一档「光栅层」**，不是把 PS 的像素工作流整体搬过来。
>
> 📌 本报告的档位判断（A/B/C）**依赖"当前后端"**；若后端换代，档位需重评。

## §2 迁移性分级（对 Vinart 的价值所在）

分四档：**A 浏览器原生可直接做** / **B 需 SVG（也是原生，但要用对 API）** / **C 需光栅后端（WebGPU/WASM）** / **D 不可迁移或不该迁移**。

| PS 能力域 | 关键项 | 档 | 落在什么上 |
|---|---|---|---|
| **图层：堆叠/组/不透明度** | 图层、组、opacity | **A** | Vinart 已有（DOM 顺序 + `opacity`） |
| **图层：混合模式** | 27 种 | **A/B** | CSS `mix-blend-mode` **支持 16/27**；canvas `globalCompositeOperation` 支持另一批；**WebGPU 可自实现全部 27** |
| **图层样式** | 投影·内阴影·外发光·内发光·颜色/渐变/图案叠加·描边 | **A** | `box-shadow` / `text-shadow` / `filter:drop-shadow` / `background-blend-mode` / `outline`；⚠️ **斜面和浮雕难**（需多层或 SVG） |
| **蒙版** | 图层蒙版 / 矢量蒙版 / 剪贴蒙版 | **A/B** | CSS `mask-*` / `clip-path` / SVG `<clipPath>`+`<mask>` |
| **智能对象 / 智能滤镜** | 无损、可替换内容 | **B** | 概念可映射为"引用素材 + 非破坏效果链"，需自建 |
| **调色：基础** | 亮度/对比/饱和/色相/反相/去色/模糊 | **A** | **CSS `filter`**（原生+GPU） |
| **调色：进阶** | 曲线/色阶/通道混合/渐变色相 | **B** | **SVG filter primitives**（见 §3 洞察 1）——原生+GPU |
| **文字** | 字符/段落/路径文字/变形 | **A/B** | HTML/CSS 是最强项；路径文字/变形 → SVG `<textPath>`/`<textLength>` |
| **矢量路径** | 钢笔/锚点/路径运算 | **B** | **SVG `<path>`**；⚠️ 路径运算需几何库 |
| **变换** | 自由变换/斜切/透视 | **A** | CSS `transform`（Vinart 已有 rotate/skewX） |
| **变换：变形** | Warp / Puppet Warp | **C** | 需网格变形 → WebGPU/WASM |
| **选区** | 智能选区/选择并遮住 | **C** | 浏览器**无原生"选区"概念**——本质是 alpha mask，需自建 |
| **绘画/画笔** | 笔刷引擎/压感/纹理笔刷 | **C** | 需 **canvas2d/WebGPU 自建画笔引擎**（最难的一块） |
| **液化** | Liquify 全套 | **C** | 需 WebGPU 网格/位移 |
| **滤镜：模糊画廊** | 场/光圈/倾斜/路径模糊 | **B/C** | 简单模糊可用 CSS/SVG；**路径/场模糊需自建** |
| **修复/润饰** | 污点修复/内容识别填充 | **C** | 需算法（WASM）或**AI 模型（外部 API）** |
| **AI 生成式** | Fill/Expand/Generate/Harmonize | **D→已有** | Vinart **已有生图链路**（`generate_assets` + 生图模型）——范式不同但覆盖同类需求 |
| **自动化/脚本** | Actions/批处理 | **D** | Vinart 的等价物是**对话链路 + 工具**（比 Actions 更强，自然语言驱动） |
| **输出/格式** | PNG/JPEG/WebP/PDF/SVG | **A/B** | canvas `toBlob`；PDF/SVG 需库 |
| **Content Credentials** | C2PA 溯源 | **A** | ⭐ **合规相关**，可直接嵌元数据（见 §3 洞察 4） |
| **3D** | —— | **D** | PS 自己都停了，**不该迁移** |

## §3 关键洞察（决定"要不要新后端"）

### 洞察 1：⭐ **SVG filter primitives = 浏览器原生的图像处理算子库**

这是整个调查里最有价值的一条。**SVG 的滤镜原语既是声明式的、又是原生+GPU 执行的**：

| SVG 原语 | 等价于 PS 的 |
|---|---|
| `feGaussianBlur` | 高斯模糊 |
| `feColorMatrix` | 通道混合器 / 色相旋转 / 饱和度 / 可做**亮度·对比** |
| `feComponentTransfer` | **曲线 / 色阶 / 伽马**（逐通道映射函数） |
| `feBlend` / `feComposite` | **混合模式 / 蒙版合成** |
| `feMorphology` | 腐蚀/膨胀（描边加粗、瘦身） |
| `feDisplacementMap` | 位移扭曲（可做**液化/波浪**的雏形） |
| `feTurbulence` | 噪声/纹理（**颗粒**） |
| `feSpecularLighting` / `feDiffuseLighting` | **光照效果** |
| `feOffset` + `feMerge` | 投影（多层偏移） |
| `feConvolveMatrix` | **自定义卷积核** |

⇒ **很多"看起来需要写 C++/GPU 的算子，SVG filter 已经原生提供了。** 这把"必须新后端"的面积**显著缩小**。

### 洞察 2：CSS `filter` 已经白送一批算子

`blur / brightness / contrast / saturate / hue-rotate / grayscale / sepia / invert / drop-shadow` —— **全部原生+GPU**，Chromium 内部是 Skia（C++）。

### 洞察 3：**混合模式是真瓶颈也是真机会**

- CSS `mix-blend-mode` 只覆盖 **16/27**（缺 `subtract`/`divide`/`linear-burn`/`vivid-light` 等）；
- canvas `globalCompositeOperation` 覆盖另一批，但也不全；
- ⇒ **要 27 全支持，需 WebGPU 自实现**（逐像素公式，天然并行）。

### 洞察 4：⭐ **Content Credentials（C2PA）与项目的合规需求直接咬合**

PS 已内置 **Content Credentials（C2PA 溯源元数据）**。而本项目的已知合规约束是：
**Amazon 2026-06-06 起**要求含 AI 生成人物的图，在文件 **XMP `dc:subject`** 加 `contains-synthetic-performer`；**EU AI Act 第 50 条**要求机器可读标记。

⇒ 这块 **不需要光栅后端**，是**元数据写入**（PNG/JPEG 的 XMP chunk），**浏览器侧或 Node 侧都能做**。属**高价值、低成本**。

### 洞察 5：**选区系统在浏览器里没有对应物**

PS 的"选区"是一等公民（可存为通道、参与所有运算）。浏览器**没有这个概念**——它等价于 **alpha 蒙版**。所以要补选区，等于**自建一套 mask 数据模型 + 编辑工具**，是"光栅层"真正的工作量所在。

### 洞察 6：**PS 的核心不是"滤镜多"，是"像素可编辑 + 自有引擎"**

把 14 个域分成两类看：
- **声明式可表达的**（图层、样式、调色、文字、矢量、变换、混合模式）→ 占**大半**，且多数有浏览器原生路径；
- **必须像素级的**（画笔、液化、选区、修复）→ 是 PS 的**护城河**，也正是"混合协议"要新增的那一档。

⇒ 结论：**"PS 化"不是抄 PS，而是给声明式模型补一档 `backend: 'raster'`。** 与 `docs/EDITOR-EVOLUTION.md` M4 的接口设计一致。

## §5 一句话总结

**PS 的 14 个能力域里，多数（图层/样式/调色/文字/矢量/变换/混合）落在"浏览器原生或 SVG 就能做"的范围内**，
真正的"必须新后端"面积比直觉小得多——**集中在画笔、液化、选区、修复这四块**。
而 **SVG filter 原语**与 **CSS filter** 是两个被低估的"原生算子库"，
**Content Credentials/C2PA** 则是与本项目合规需求直接咬合、且成本最低的一项。

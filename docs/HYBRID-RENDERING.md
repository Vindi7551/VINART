# 混合渲染可行性实验报告

> **日期**：2026-10-12
> **目的**：回答一个问题——**不换渲染后端（HTML+CSS+Chromium），能走多远？"混合渲染"（DOM 层 + 光栅层）能不能现在就做？**
> **性质**：**实验报告 + 踩坑记录**。所有结论都有可复现的探针与数字支撑。
> **相关**：`docs/PHOTOSHOP-CAPABILITIES.md`（PS 能力全景）、`docs/EDITOR-EVOLUTION.md`（编辑器演进，M4 已预留 `backend:'dom'|'raster'`）。
> **探针目录**：`scripts/_probe-dom-capability/`（HTML 页面 + Python 工具 + 产物 PNG）

| # | 结论 | 证据 |

| **1** | **DOM 的上限比直觉高得多**：33 条 PS 能力里，**26 条可直接做**、**2 条需额外引擎**、**仅 5 条真需光栅/模型** | 能力账本 4 页实测（§3） |

## §1 背景

用户方向（本节的地基）：

1. **第一步是"榨干 HTML+CSS 的表达上限"**，之后才谈混合协议；
2. 契约（`design-sketch`）当初是**为快速验证可行性而设计**的，很多地方要重新调整；
3. **自建渲染器是长期目标**，但**不该现在假定后端固定**——未来可能是 `DOM + 光栅` 混合。

本轮把 1 做成了实测，并顺带验证了 3 的可行性边界。

## §4 实验二 · `isolation:isolate` 会不会挡住 `mix-blend-mode`？

### 缘起（我的预判）
Vinart 的节点容器带 **`isolation:isolate`**（`render.ts`，为压制内部 `z-index` 外逃）。我**预判**它会切断光栅层与 DOM 层的混合——如果成立，用户的"加一层透明图层再混合"就要先动拆层机制。

### 方法（可复现）
1. `paint-layer.html` → 用 Chrome `--default-background-color=00000000` 渲出**真 RGBA 光栅层** `paint-layer.png`（728×532，**colorType=6**，笔刷状笔画）。
2. `05-raw.html`：三段**严格等尺寸堆叠**（各 250px 高），唯一变量 = 容器 `isolation` + 光栅层 `mix-blend-mode`：
   - **A** = `isolation:isolate` + `multiply`
   - **B** = `isolation:auto` + `multiply`
   - **C** = 无混合模式（基准）
3. `compare.py`：**自写 PNG 解码**，**逐像素**求平均绝对差。

### 结果（硬数字）
```
全幅   mean|A-B| = 0.0258      mean|A-C| = 1.9976
笔画区 mean|A-B| = 0.0203      mean|A-C| = 5.3188

① isolation 不挡混合 ✅（A 与 B 逐像素几乎相同，0.02 = 抗锯齿噪声）
② 混合确实生效   ✅（笔画区 A-C 是 A-B 的 263 倍）
```

### 结论
**`isolation:isolate` 不挡 `mix-blend-mode`**——因为 `isolation` 隔离的是**元素的后代**，元素**自身**的 `mix-blend-mode` 仍在**父层叠上下文**里解析。

⇒ 用户的"**加一层透明光栅图层 → 混合**"**开箱即用**：不用动 `isolation`、不用改拆层机制。
⚠️ 但 **CSS 混合仍受 `mix-blend-mode` 只覆盖 16/27 种**的天花板限制。

## §5 实验三 · 变换型流水线（烘焙 → 光栅操作 → 回填）

### 为什么还要测这个
§4 验证的是**叠加型**（加一层）。但还有**变换型**：光栅操作要作用在**已有的 DOM 层**上（如"把商品图边缘做出笔刷撕裂感"）。那就得**先栅格化、再操作、再回填**。

### 三步流水线（各步独立可跑可验）

| 步 | 文件 → 产物 | 做什么 |
|---|---|---|
| **① 烘焙** | `step1-dom-layer.html` → `dom-layer.png` | DOM 声明式层（圆角/渐变/文字/描边环）**烘焙**成位图（Chrome 透明底截图） |
| **② 光栅操作** | `step2-raster-op.html` → `raster-result.png` | Canvas 做 **DOM 做不到的两件事** |
| **③ 回填合成** | `step3-final.html` → `out-06-*.png` | DOM 底板（渐变）+ 光栅层 + DOM 文字层 |

**②里的两件事**：
- **局部推挤变形**——逐条带水平位移 + 二次衰减（**空间变化的 warp**，CSS/SVG 的均匀 `transform` 给不了）；
- **笔刷盖章**——软边径向渐变圆点沿 S 形路径**变半径累积**（半径正弦变化 = 压感效果）。

### 断言（`assert-bake-op.py`，4/4 通过）
```
① dom-layer.png     420x300 ch=4 colorType=6      ← RGBA，烘焙出的是"图层"不是整幅
② raster-result.png 420x300 ch=4 colorType=6      ← 保留 alpha，alpha 覆盖 78.6%
   ①与② mean|Δ| = 19.96                            ← 光栅操作确实改了像素（非空跑）
回归：compare.py 仍 EXIT=0                          ← §4 的结论未被破坏
```

### 结论
**变换型路径完整跑通**：`DOM 渲染 → 栅格化 → 像素域操作 → 当普通图层回填`，与既有渲染管线**无缝**（回填后的光栅层就是一张 `<img>`，垫在 DOM 底板、压在 DOM 文字下）。

## §6 实验四 · 程序化生成（算法产数据 → DOM 渲染）

### 为什么还要测这个
§3 的能力账本把**变宽笔触**判为 ❌（04 页负例）。但那条判定有个隐含假设——**数据必须由"命名 / 手写"给出**。
而实际上一大批"看起来需要光栅"的效果，落点是**「算法算出数据 + DOM 渲染」**：这是 §9.1 三层射程里的**第 ② 层**，也是**最容易被低估**的一格。

### 方法
`06-programmatic-gen.html` —— **6 个场景全部由页内 JS 用种子化 PRNG（mulberry32）现算现渲**，输出 SVG 标记（真实运行，不是静态图）：

| 场景 | 手法 |
|---|---|
| **撕纸边** | 沿矩形四边按噪声扰动算出**闭合路径** → 当 `clipPath` 裁图 |
| **毛边条带 / 丝带** | 上下两条毛边曲线闭合填充 |
| **⭐ 变宽笔触** | 沿中心线求**法向偏移**生成闭合轮廓再填充 |
| **沿路径盖章** | 算出 N 个椭圆（位置 / 半径 / 角度带抖动）→ 逐个渲染、透明度累积 |
| **程序化图案** | 种子化点阵 + 抖动 + 半径渐变 |
| **手绘感边框** | 两条轻微错位的毛边闭合曲线叠加（马克笔框） |

### 结果

1. **§3 的 ❌ 变成 ✅**：变宽笔触用"**法向偏移算轮廓**"实现 —— `stroke-width` 给不了的"由粗到细"，**算出来就有了**，且形态像真实笔触。
2. **确定性断言通过**（`assert-deterministic.py`，复用 `pnglib`）：
   ```
   同一页面渲染两次 → mean|Δ| = 0.000000   （1180x800，逐像素完全相同）
   ```
   ⇒ 生成是**确定性的、给定种子即可复现** —— 正好对上项目原则「**渲染 = 确定性纯函数**」（若用了 `Math.random()` 这类非确定性源，这条断言会失败）。

### 结论

> **第 ② 层的存在，显著抬高了"DOM 上限"**：很多被直觉判为"要光栅"的效果，
> 真正的落点是「**确定性算法 + DOM 渲染**」，而不是新后端。

## §9 架构结论与路线

### 8.1 三层射程（不是两层）

| 层 | 内容 | 谁产出 | 留在 DOM？ |
|---|---|---|---|
| **① 声明式** | rect / text / 图片 / 命名形状 | LLM | ✅ |
| **② 程序化生成**（易被忽略的中间层） | 笔刷掩版、撕边、位移图、盖章序列 | **确定性代码**（或人手/模型） | ✅ **仍渲染在 DOM/SVG** |
| **③ 光栅** | 实时笔刷、像素累积、液化、变形、修复 | 人（编辑器）+ GPU | ❌ 需新后端 |

### 8.2 混合渲染的两条路线

| | **路线 A：HTML 当最终合成器** | **路线 B：自建合成器** |
|---|---|---|
| 做法 | 声明式层留在 HTML；光栅层**先渲成位图**再嵌入，靠 CSS 混合合成 | 所有层变 buffer，由 WebGPU 合成 |
| 代价 | **低**（Chromium 仍是输出路径） | 高（自写渲染器） |
| 限制 | 混合限 16/27；合成控制权在 Chromium | 表达力完整 |
| 何时够 | **九成场景** | 需 27/27 + 组级合成 + 实时交互 |

**关键**：路线 A **不需要放弃 HTML**（光栅层预烘成位图即可）——§5 已实测跑通。
**升级路径的地基已在**：`blink-renderer.ts` 的 `injectCss` + `selector` 本就是"**隐藏其它、只截目标层**"（图层隔离），即"逐层栅格化"的机器 → 从 A 升到 B **不是从零造渲染器**。

### 8.3 什么情况下才真要新后端

- 混合模式要 **27/27** 或**组级混合**；
- **实时交互**绘制（60fps）；
- **像素级算子**（液化/操控变形/内容识别）；
- 需要**非图像输出**（SVG/PDF/分层）——这属于**输出轴**，与后端无关。

### 8.4 与既有设计的一致性
`docs/EDITOR-EVOLUTION.md:607`（M4）已预留 **层模型加 `backend: 'dom' | 'raster'`**；`:368` 写明「分层不是渲染机制，而是**状态转换（vector → raster）**」。本轮实验**为 M4 提供了可行性证据**。
